\hypertarget{md_chap3_autotoc_md9}{}\doxysubsubsection{Ten tasks}\label{md_chap3_autotoc_md9}
The purpose of {\ttfamily class} consists in computing some background quantities, thermodynamical quantities, perturbation transfer functions, and finally 2-\/point statistics (power spectra) for a given set of cosmological parameters. This task can be decomposed in few steps or modules\+:


\begin{DoxyEnumerate}
\item set input parameter values.
\item compute the evolution of cosmological background quantities.
\item compute the evolution of thermodynamical quantities (ionization fractions, etc.)
\item compute the evolution of source functions $S(k,\tau)$ (by integrating over all perturbations).
\item compute the primordial spectra.
\item eventually, compute non-\/linear corrections at small redshift/large wavenumber.
\item compute transfer functions in harmonic space $\Delta_l(k)$ (unless one needs only Fourier spectra $P(k)$\textquotesingle{}s and no harmonic spectra $C_l$\textquotesingle{}s).
\item compute the observable power spectra $C_l$\textquotesingle{}s (by convolving the primordial spectra and the harmonic transfer functions) and/or $P(k)$\textquotesingle{}s (by multiplying the primordial spectra and the appropriate source functions $S(k,\tau)$).
\item eventually, compute the lensed CMB spectra (using second-\/order perturbation theory)
\item write results in files (when {\ttfamily CLASS} is used interactively. The python wrapper does not go through this step, after 1.-\/9. it just keeps the output stored internally).
\end{DoxyEnumerate}\hypertarget{md_chap3_autotoc_md10}{}\doxysubsubsection{Ten structures}\label{md_chap3_autotoc_md10}
In {\ttfamily class}, each of these steps is associated with a structure\+:


\begin{DoxyEnumerate}
\item {\ttfamily struct precision} for input precision parameters (input physical parameters are dispatched among the other structures listed below)
\item {\ttfamily struct background} for cosmological background,
\item {\ttfamily struct thermo} for thermodynamics,
\item {\ttfamily struct perturbs} for source functions,
\item {\ttfamily struct primordial} for primordial spectra,
\item {\ttfamily struct nonlinear} for nonlinear corrections,
\item {\ttfamily struct transfers} for transfer functions,
\item {\ttfamily struct spectra} for observable spectra,
\item {\ttfamily struct lensing} for lensed CMB spectra,
\item {\ttfamily struct output} for auxiliary variable describing the output format.
\end{DoxyEnumerate}

A given structure contains \char`\"{}everything concerning one step that the subsequent steps need to know\char`\"{} (for instance, {\ttfamily struct perturbs} contains everything about source functions that the transfer module needs to know). In particular, each structure contains one array of tabulated values (for {\ttfamily struct background}, background quantities as a function of time, for {\ttfamily struct thermo}, thermodynamical quantities as a function of redshift, for {\ttfamily struct perturbs}, sources $S(k, \tau)$, etc.). It also contains information about the size of this array and the value of the index of each physical quantity, so that the table can be easily read and interpolated. Finally, it contains any derived quantity that other modules might need to know. Hence, the communication from one module A to another module B consists in passing a pointer to the structure filled by A, and nothing else.

All \char`\"{}precision parameters\char`\"{} are grouped in the single structure {\ttfamily struct precision}. The code contains {\itshape no other arbitrary numerical coefficient}.\hypertarget{md_chap3_autotoc_md11}{}\doxysubsubsection{Ten modules}\label{md_chap3_autotoc_md11}
Each structure is defined and filled in one of the following modules (and precisely in the order below)\+:


\begin{DoxyEnumerate}
\item {\ttfamily \mbox{\hyperlink{input_8c}{input.\+c}}}
\item {\ttfamily \mbox{\hyperlink{background_8c}{background.\+c}}}
\item {\ttfamily \mbox{\hyperlink{thermodynamics_8c}{thermodynamics.\+c}}}
\item {\ttfamily \mbox{\hyperlink{perturbations_8c}{perturbations.\+c}}}
\item {\ttfamily \mbox{\hyperlink{primordial_8c}{primordial.\+c}}}
\item {\ttfamily \mbox{\hyperlink{nonlinear_8c}{nonlinear.\+c}}}
\item {\ttfamily \mbox{\hyperlink{transfer_8c}{transfer.\+c}}}
\item {\ttfamily \mbox{\hyperlink{spectra_8c}{spectra.\+c}}}
\item {\ttfamily \mbox{\hyperlink{lensing_8c}{lensing.\+c}}}
\item {\ttfamily \mbox{\hyperlink{output_8c}{output.\+c}}}
\end{DoxyEnumerate}

Each of these modules contains at least three functions\+:


\begin{DoxyItemize}
\item {\ttfamily module\+\_\+init(...)}
\item {\ttfamily module\+\_\+free(...)}
\item {\ttfamily module\+\_\+something\+\_\+at\+\_\+somevalue}
\end{DoxyItemize}

where {\itshape module} is one of {\ttfamily input, background, thermodynamics, perturb, primordial, nonlinear, transfer, spectra, lensing, output}.

The first function allocates and fills each structure. This can be done provided that the previous structures in the hierarchy have been already allocated and filled. In summary, calling one of {\ttfamily module\+\_\+init(...)} amounts in solving entirely one of the steps 1 to 10.

The second function deallocates the fields of each structure. This can be done optionally at the end of the code (or, when the code is embedded in a sampler, this {\bfseries{must}} be done between each execution of {\ttfamily class}, and especially before calling {\ttfamily module\+\_\+init(...)} again with different input parameters).

The third function is able to interpolate the pre-\/computed tables. For instance, {\ttfamily \mbox{\hyperlink{background_8c_afeb0656453b92be39c60fb3fb1abd910}{background\+\_\+init()}}} fills a table of background quantities for discrete values of conformal time $\tau$, but {\ttfamily background\+\_\+at\+\_\+tau(tau, $\ast$ values)} will return these values for any arbitrary $\tau$.

Note that functions of the type {\ttfamily module\+\_\+something\+\_\+at\+\_\+somevalue} are the only ones which are called from another module, while functions of the type {\ttfamily module\+\_\+init(...)} and {\ttfamily module\+\_\+free(...)} are the only one called by the main executable. All other functions are for internal use in each module.

When writing a C code, the ordering of the functions in the $\ast$.c file is in principle arbitrary. However, for the sake of clarity, we always respected the following order in each {\ttfamily CLASS} module\+:


\begin{DoxyEnumerate}
\item all functions that may be called by other modules, i.\+e. \char`\"{}external functions\char`\"{}, usually named like {\ttfamily module\+\_\+something\+\_\+at\+\_\+somevalue(...)}
\item then, {\ttfamily module\+\_\+init(...)}
\item then, {\ttfamily module\+\_\+free()}
\item then, all functions used only internally by the module
\end{DoxyEnumerate}\hypertarget{md_chap3_autotoc_md12}{}\doxysubsection{The  $<$tt$>$main()$<$/tt$>$ function(s)}\label{md_chap3_autotoc_md12}
\hypertarget{md_chap3_autotoc_md13}{}\doxysubsubsection{The  $<$tt$>$main.\+c$<$/tt$>$ file}\label{md_chap3_autotoc_md13}
The main executable of {\ttfamily class} is the function {\ttfamily main()} located in the file {\ttfamily main/main.\+c}. This function consist only in the following lines (not including comments and error-\/management lines explained later)\+: \begin{DoxyVerb}main() {
 struct precision pr;

 struct background ba;

 struct thermo th;

 struct perturbs pt;

 struct primordial pm;

 struct nonlinear nl;

 struct transfers tr;

 struct spectra sp;

 struct lensing le;

 struct output op;


 input_init_from_arguments(argc, argv,&pr,&ba,&th,&pt,&tr,&pm,&sp,&nl,&le,&op,errmsg);

 background_init(&pr,&ba);

 thermodynamics_init(&pr,&ba,&th);

 perturb_init(&pr,&ba,&th,&pt);

 primordial_init(&pr,&pt,&pm);

 nonlinear_init(&pr,&ba,&th,&pt,&pm,&nl);

 transfer_init(&pr,&ba,&th,&pt,&nl,&tr);

 spectra_init(&pr,&ba,&pt,&pm,&nl,&tr,&sp);

 lensing_init(&pr,&pt,&sp,&nl,&le);

 output_init(&ba,&th,&pt,&pm,&tr,&sp,&nl,&le,&op)


 /****** done ******/


 lensing_free(&le);

 spectra_free(&sp);

 transfer_free(&tr);

 nonlinear_free(&nl);

 primordial_free(&pm);

 perturb_free(&pt);

 thermodynamics_free(&th);

 background_free(&ba);
\end{DoxyVerb}


We can come back on the role of each argument. The arguments above are all pointers to the 10 structures of the code, excepted {\ttfamily argc, argv} which contains the input files passed by the user, and {\ttfamily errmsg} which contains the output error message of the input module (error management will be described below).

{\ttfamily input\+\_\+init\+\_\+from\+\_\+arguments} needs all structures, because it will set the precision parameters inside the {\ttfamily precision} structure, and the physical parameters in some fields of the respective other structures. For instance, an input parameter relevant for the primordial spectrum calculation (like the tilt $n_s$) will be stored in the {\ttfamily primordial} structure. Hence, in {\ttfamily input\+\_\+init\+\_\+from\+\_\+arguments}, all structures can be seen as output arguments.

Other {\ttfamily module\+\_\+init()} functions typically need all previous structures, which contain the result of the previous modules, plus its own structures, which contain some relevant input parameters before the function is called, as well as all the result form the module when the function has been executed. Hence all passed structures can be seen as input argument, excepted the last one which is both input and output. An example is {\ttfamily perturb\+\_\+init(\&pr,\&ba,\&th,\&pt)}.

Each function {\ttfamily module\+\_\+init()} does not need {\bfseries{all}} previous structures, it happens that a module does not depend on a {\bfseries{all}} previous one. For instance, the primordial module does not need information on the background and thermodynamics evolution in order to compute the primordial spectra, so the dependency is reduced\+: {\ttfamily primordial\+\_\+init(\&pr,\&pt,\&pm)}.

Each function {\ttfamily module\+\_\+init()} only deallocates arrays defined in the structure of their own module, so they need only their own structure as argument. (This is possible because all structures are self-\/contained, in the sense that when the structure contains an allocated array, it also contains the size of this array). The first and last module, {\ttfamily input} and {\ttfamily output}, have no {\ttfamily input\+\_\+free()} or {\ttfamily output\+\_\+free()} functions, because the structures {\ttfamily precision} and {\ttfamily output} do not contain arrays that would need to be de-\/allocated after the execution of the module.\hypertarget{md_chap3_autotoc_md14}{}\doxysubsubsection{The $<$tt$>$test\+\_\+$<$...$>$.\+c$<$/tt$>$ files}\label{md_chap3_autotoc_md14}
For a given purpose, somebody could only be interested in the intermediate steps (only background quantities, only the thermodynamics, only the perturbations and sources, etc.) It is then straightforward to truncate the full hierarchy of modules 1, ... 10 at some arbitrary order. We provide several \char`\"{}reduced executables\char`\"{} achieving precisely this. They are located in {\ttfamily test/test\+\_\+module\+\_\+.\+c} (like, for instance, {\ttfamily test/test\+\_\+perturbations.\+c}) and they can be complied using the Makefile, which contains the appropriate commands and definitions (for instance, you can type {\ttfamily make test\+\_\+perturbations}).

The {\ttfamily test/} directory contains other useful example of alternative main functions, like for instance {\ttfamily test\+\_\+loops.\+c} which shows how to call {\ttfamily CLASS} within a loop over different parameter values. There is also a version {\ttfamily test/test\+\_\+loops\+\_\+omp.\+c} using a double level of open\+MP parallelisation\+: one for running several {\ttfamily CLASS} instances in parallel, one for running each {\ttfamily CLASS} instance on several cores. The comments in these files are self-\/explanatory.\hypertarget{md_chap3_autotoc_md15}{}\doxysection{Input/output}\label{md_chap3_autotoc_md15}
\hypertarget{md_chap3_autotoc_md16}{}\doxysubsection{Input}\label{md_chap3_autotoc_md16}
There are two types of input\+:


\begin{DoxyItemize}
\item \char`\"{}precision parameters\char`\"{} (controlling the precision of the output and the execution time),
\item \char`\"{}input parameters\char`\"{} (cosmological parameters, flags telling to the code what it should compute, ...)
\end{DoxyItemize}

The code can be executed with a maximum of two input files, e.\+g. \begin{DoxyVerb} ./class explanatory.ini cl_permille.pre
\end{DoxyVerb}


The file with a {\ttfamily .ini} extension is the cosmological parameter input file, and the one with a {\ttfamily .pre} extension is the precision file. Both files are optional\+: all parameters are set to default values corresponding to the \char`\"{}most usual choices\char`\"{}, and are eventually replaced by the parameters passed in the two input files. For instance, if one is happy with default accuracy settings, it is enough to run with \begin{DoxyVerb} ./class explanatory.ini
\end{DoxyVerb}
 Input files do not necessarily contain a line for each parameter, since many of them can be left to default value. The example file {\ttfamily explanatory.\+ini} is very long and somewhat indigestible, since it contains all possible parameters, together with lengthy explanations. We recommend to keep this file unchanged for reference, and to copy it in e.\+g. {\ttfamily test.\+ini}. In the latter file, the user can erase all sections in which he/she is absolutely not interested (e.\+g., all the part on isocurvature modes, or on tensors, or on non-\/cold species, etc.). Another option is to create an input file from scratch, copying just the relevant lines from {\ttfamily explanatory.\+ini}. For the simplest applications, the user will just need a few lines for basic cosmological parameters, one line for the {\ttfamily output} entry (where one can specifying which power spectra must be computed), and one line for the {\ttfamily root} entry (specifying the prefix of all output files).

The syntax of the input files is explained at the beginning of {\ttfamily explanatory.\+ini}. Typically, lines in those files look like\+:

\begin{DoxyVerb}  parameter1 = value1

  free comments

  parameter2 = value2 # further comments

  # commented_parameter = commented_value
\end{DoxyVerb}
 and parameters can be entered in arbitrary order. This is rather intuitive. The user should just be careful not to put an \char`\"{}=\char`\"{} sign not preceded by a \char`\"{}\#\char`\"{} sign inside a comment\+: the code would then think that one is trying to pass some unidentified input parameter.

The syntax for the cosmological and precision parameters is the same. It is clearer to split these parameters in the two files {\ttfamily .ini} and {\ttfamily .pre}, but there is no strict rule about which parameter goes into which file\+: in principle, precision parameters could be passed in the {\ttfamily .ini}, and vice-\/versa. The only important thing is not to pass the same parameter twice\+: the code would then complain and not run.

The {\ttfamily CLASS} input files are also user-\/friendly in the sense that many different cosmological parameter bases can be used. This is made possible by the fact that the code does not only read parameters, it \char`\"{}interprets them\char`\"{} with the level of logic which has been coded in the {\ttfamily \mbox{\hyperlink{input_8c}{input.\+c}}} module. For instance, the Hubble parameter, the photon density, the baryon density and the ultra-\/relativistic neutrino density can be entered as\+: \begin{DoxyVerb}  h = 0.7

  T_cmb = 2.726     # Kelvin units

  omega_b = 0.02

  N_eff = 3.04
\end{DoxyVerb}


(in arbitrary order), or as

\begin{DoxyVerb}  H0 = 70

  omega_g = 2.5e-5     # g is the label for photons

  Omega_b = 0.04

  omega_ur = 1.7e-5    # ur is the label for ultra-relativistic species
\end{DoxyVerb}


or any combination of the two. The code knows that for the photon density, one should pass one (but not more than one) parameter out of {\ttfamily T\+\_\+cmb}, {\ttfamily omega\+\_\+g}, {\ttfamily Omega\+\_\+g} (where small omega\textquotesingle{}s refer to $\omega_i \equiv \Omega_i h^2$). It searches for one of these values, and if needed, it converts it into one of the other two parameters, using also other input parameters. For instance, {\ttfamily omega\+\_\+g} will be converted into {\ttfamily Omega\+\_\+g} even if $h$ is written later in the file than {\ttfamily omega\+\_\+g}\+: the order makes no difference. Lots of alternatives have been defined. If the code finds that not enough parameters have been passed for making consistent deductions, it will complete the missing information with in-\/built default values. On the contrary, if it finds that there is too much information and no unique solution, it will complain and return an error.

In summary, the input syntax has been defined in such way that the user does not need to think too much, and can pass his preferred set of parameters in a nearly informal way.

Let us mention a two useful parameters defined at the end of {\ttfamily explanatory.\+ini}, that we recommend setting to {\ttfamily yes} in order to run the code in a safe way\+:

{\ttfamily write parameters = \mbox{[}yes or no\mbox{]}} ({\itshape default}\+: {\ttfamily no})

When set to yes, all input/precision parameters which have been read are written in a file {\ttfamily $<$root$>$parameters.\+ini}, to keep track all the details of this execution; this file can also be re-\/used as a new input file. Also, with this option, all parameters that have been passed and that the code did not read (because the syntax was wrong, or because the parameter was not relevant in the context of the run) are written in a file {\ttfamily $<$root$>$unused\+\_\+parameters}. When you have doubts about your input or your results, you can check what is in there.

{\ttfamily write warnings = \mbox{[}yes or no\mbox{]}} ({\itshape default}\+: {\ttfamily no})

When set to yes, the parameters that have been passed and that the code did not read (because the syntax was wrong, or because the parameter was not relevant in the context of the run) are written in the standard output as {\ttfamily \mbox{[}Warning\+:\mbox{]}....}

There is also a list of \char`\"{}verbose\char`\"{} parameters at the end of {\ttfamily explanatory.\+ini}. They can be used to control the level of information passed to the standard output (0 means silent; 1 means normal, e.\+g. information on age of the universe, etc.; 2 is useful for instance when you want to check on how many cores the run is parallelised; 3 and more are intended for debugging).

{\ttfamily CLASS} comes with a list of precision parameter files ending by {\ttfamily .pre}. Honestly we have not been updating all these files recently, and we need to do a bit of cleaning there. However you can trust {\ttfamily cl\+\_\+ref.\+pre}. We have derived this file by studying both the convergence of the CMB output with respect to all {\ttfamily CLASS} precision parameters, and the agreement with {\ttfamily CAMB}. We consider that this file generates good reference CMB spectra, accurate up to the hundredth of per cent level, as explained in the CLASS IV paper and re-\/checked since then. You can try it with e.\+g. \begin{DoxyVerb}./class explanatory.ini cl_ref.pre
\end{DoxyVerb}
 but the run will be extremely long. This is an occasion to run a many-\/core machine with a lot of RAM. It may work also on your laptop, but in half an hour or so.

If you want a reference matter power spectrum P(k), also accurate up to the hundredth of percent level, we recommend using the file {\ttfamily pk\+\_\+ref.\+pre}, identical to {\ttfamily cl\+\_\+ref.\+pre} excepted that the truncation of the neutrino hierarchy has been pushed to {\ttfamily l\+\_\+max\+\_\+ur=150}.

In order to increase moderately the precision to a tenth of percent, without prohibitive computing time, we recommend using {\ttfamily cl\+\_\+permille.\+pre}.\hypertarget{md_chap3_autotoc_md17}{}\doxysubsection{Output}\label{md_chap3_autotoc_md17}
The input file may contain a line \begin{DoxyVerb}  root = <root>
\end{DoxyVerb}
 where {\ttfamily $<$root$>$} is a path of your choice, e.\+g. {\ttfamily output/test\+\_\+}. Then all output files will start like this, e.\+g. {\ttfamily output/test\+\_\+cl.\+dat}, {\ttfamily output/test\+\_\+cl\+\_\+lensed.\+dat}, etc. Of course the number of output files depends on your settings in the input file. There can be input files for CMB, LSS, background, thermodynamics, transfer functions, primordial spectra, etc. All this is documented in {\ttfamily explanatory.\+ini}.

If you do not pass explicitly a {\ttfamily root = $<$root$>$}, the code will name the output in its own way, by concatenating {\ttfamily output/}, the name of the input parameter file, and the first available integer number, e.\+g. \begin{DoxyVerb} output/explanatory03_cl.dat, etc.
\end{DoxyVerb}
\hypertarget{md_chap3_autotoc_md18}{}\doxysection{General principles}\label{md_chap3_autotoc_md18}
\hypertarget{md_chap3_autotoc_md19}{}\doxysubsection{Error management}\label{md_chap3_autotoc_md19}
Error management is based on the fact that all functions are defined as integers returning either {\ttfamily \+\_\+\+SUCCESS\+\_\+} or {\ttfamily \+\_\+\+FAILURE\+\_\+}. Before returning {\ttfamily \+\_\+\+FAILURE\+\_\+}, they write an error message in the structure of the module to which they belong. The calling function will read this message, append it to its own error message, and return a {\ttfamily \+\_\+\+FAILURE\+\_\+}; and so on and so forth, until the main routine is reached. This error management allows the user to see the whole nested structure of error messages when an error has been met. The structure associated to each module contains a field for writing error messages, called {\ttfamily structure\+\_\+i.\+error\+\_\+message}, where {\ttfamily structure\+\_\+i} could be one of {\ttfamily background}, {\ttfamily thermo}, {\ttfamily perturbs}, etc. So, when a function from a module $i$ is called within module $j$ and returns an error, the goal is to write in {\ttfamily structure\+\_\+j.\+error\+\_\+message} a local error message, and to append to it the error message in {\ttfamily structure\+\_\+i.\+error\+\_\+message}. These steps are implemented in a macro {\ttfamily class\+\_\+call()}, used for calling whatever function\+:

\begin{DoxyVerb}  class_call(module_i_function(...,structure_i),
            structure_i.error_message,
            structure_j.error_message);
\end{DoxyVerb}


So, the first argument of {\ttfamily call\+\_\+call()} is the function we want to call; the second argument is the location of the error message returned by this function; and the third one is the location of the error message which should be returned to the higher level. Usually, in the bulk of the code, we use pointer to structures rather than structure themselves; then the syntax is \begin{DoxyVerb}  class_call(module_i_function(...,pi),
         pi->error_message,
         pj->error_message);`
\end{DoxyVerb}
 where in this generic example, {\ttfamily pi} and {\ttfamily pj} are assumed to be pointers towards the structures {\ttfamily structure\+\_\+i} and {\ttfamily structure\+\_\+j}.

The user will find in {\ttfamily \mbox{\hyperlink{common_8h}{include/common.\+h}}} a list of additional macros, all starting by {\ttfamily class\+\_\+...()}, which are all based on this logic. For instance, the macro {\ttfamily class\+\_\+test()} offers a generic way to return an error in a standard format if a condition is not fulfilled. A typical error message from {\ttfamily CLASS} looks like\+:

{\ttfamily Error in module\+\_\+j\+\_\+function1}

{\ttfamily module\+\_\+j\+\_\+function1 (L\+:340) \+: error in module\+\_\+i\+\_\+function2(...)}

{\ttfamily module\+\_\+i\+\_\+function2 (L\+:275) \+: error in module\+\_\+k\+\_\+function3(...)}

{\ttfamily ...}

{\ttfamily =$>$ module\+\_\+x\+\_\+functionN (L\+:735) \+: your choice of input parameter blabla=30 is not consistent with the constraint blabla$<$1}

where the {\ttfamily L}\textquotesingle{}s refer to line numbers in each file. These error messages are very informative, and are built almost entirely automatically by the macros. For instance, in the above example, it was only necessary to write inside the function {\ttfamily module\+\_\+x\+\_\+function\+N()} a test like\+:

\begin{DoxyVerb}  class_test(blabla >= 1,
              px->error_message,
           "your choice of input parameter blabla=%e
  is not consistent with the constraint blabla<%e",
             blabla,blablamax);
\end{DoxyVerb}


All the rest was added step by step by the various {\ttfamily class\+\_\+call()} macros.\hypertarget{md_chap3_autotoc_md20}{}\doxysubsection{Dynamical allocation of indices}\label{md_chap3_autotoc_md20}
On might be tempted to decide that in a given array, matrix or vector, a given quantity is associated with an explicit index value. However, when modifying the code, extra entries will be needed and will mess up the initial scheme; the user will need to study which index is associated to which quantity, and possibly make an error. All this can be avoided by using systematically a dynamical index allocation. This means that all indices remain under a symbolic form, and in each, run the code attributes automatically a value to each index. The user never needs to know this value.

Dynamical indexing is implemented in a very generic way in CLASS, the same rules apply everywhere. They are explained in these lecture slides\+:

Any feature or equation which could be true in one cosmology and not in another one should not be written explicitly in the code, and should not be taken as granted in several other places. Discretization and integration steps are usually defined automatically by the code for each cosmology, instead of being set to something which might be optimal for minimal models, and not sufficient for other ones. You will find many example of this in the code. As a consequence, in the list of precision parameter, you rarely find actual stepsize. You find rather parameters representing the ratio between a stepsize and a physical quantity computed for each cosmology.\hypertarget{md_chap3_autotoc_md22}{}\doxysubsection{Modifying the code}\label{md_chap3_autotoc_md22}
Implementing a new idea completly from scratch would be rather intimidating, even for the main developpers of {\ttfamily CLASS}. Fortunately, we never have to work from scratch. Usually we want to code a new species, a new observable, a new approximation scheme, etc. The trick is to think of another species, observable, approximation scheme, etc., looking as close as possible to the new one.

Then, playing with the {\ttfamily grep} command and the {\ttfamily search} command of your editor, search for all occurences of this nearest-\/as-\/possible other feature. This is usually easy thanks to our naming scheme. For each species, observable, approximation scheme, etc., we usually use the same sequence of few letters everywhere (fo instance, {\ttfamily fld} for the fluid usually representing Dark Energy). Grep for {\ttfamily fld} and you\textquotesingle{}ll get all the lines related to the fluid. There is another way\+: we use everywhere some conditional jumps related to a given feature. For instance, the lines related to the fluid are always in between {\ttfamily if (pba-\/$>$has\+\_\+fld == \+\_\+\+TRUE\+\_\+) \{ ... \}} and the lines related to the cosmic shear observables are always in between {\ttfamily if (ppt-\/$>$has\+\_\+lensing\+\_\+potential == \+\_\+\+TRUE\+\_\+) \{ ... \}}. Locating these flags and conditional jumps shows you all the parts related to a given feature/ingredient.

Once you have localised your nearest-\/as-\/possible other feature, you can copy/paste these lines and adapt them to the case of your new feature! You are then sure that you didn\textquotesingle{}t miss any step, even the smallest technical steps (definition of indices, etc.)\hypertarget{md_chap3_autotoc_md23}{}\doxysection{Units}\label{md_chap3_autotoc_md23}
Internally, the code uses almost everywhere units of Mpc to some power, excepted in the inflation module, where many quantities are in natural units (wrt the true Planck mass).
